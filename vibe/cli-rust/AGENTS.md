# AGENTS.md — vibe-rs

A Rust/ratatui TUI for Vibe. It drives the **unchanged** Python engine over the
app-server JSON-RPC protocol.

## What this is

Rewrite the vibe cli in rust for very good performances

```txt
tui  ── render + input + reducer
client ── spawn vibe-app-server, frame NDJSON, correlate ids, forward notifs
proto  ── serde types for the SUBSET of methods/notifications we use
```

## Rules

- Do not modify code to make tests pass, modify code to fix code, and it should fix test, fix user and code first.
- Aim for very good performance, this is a PoC to see how fast we can be
- Aim for simplicity and low number of lines, this is very important
- Inspire yourself from codex/ folder, it is a good architecture and it is working well !
- Keep pure-logic tests in `tests/units/<name>.rs` and register them in `tests/units.rs` so they share one integration-test binary. Keep tests that need process-global isolation in separate `tests/<name>.rs` binaries. Cover Rust rendering and interaction behavior with `client-e2e` scenarios and goldens -- see `client-e2e/AGENTS.md`.
- No files with >300 lines of code allowed, simplicity is very important, keep things in separate modules.
- This is the rewrite of the python code, when naming things, try to keep the same names as in the python code.
- When implementing a feature, port it from the Python CLI and keep its behavior by default. Diverge only when it yields a more coherent design, a bug fix, or a better UX, or when a Rust-only feature is explicitly requested. Such divergences do not require updating the Python CLI.
- No multi line comments ! Very short modeule docstrings
- Unit tests are welcome, but never inline in source files: no `#[cfg(test)] mod tests { ... }` blocks under `src/`. Test through the crate API from `tests/` (see the layout rule above). When a test needs private items, put it in a child module file under the module's directory (`src/foo/tests.rs` for `src/foo.rs` or `src/foo/mod.rs`), declared with `#[cfg(test)] mod tests;`.

## First MVP

- We need basic conversation working, same UI by default, all other features can be there but failing gracefully like "not implemented"

## Client end-to-end scenarios

- When you spot a regression, make an exhaustive scenario. The fixture (`client-e2e/fixtures/fixture.json`) is committed and hand-maintained; there is no recorder.
- Run focused scenarios while iterating. The full gate (`make test_golden`) runs in parallel and takes well under a minute once the release binary is built, so run it before pushing.

## Golden snapshots

Committed Rust-only goldens (terminal SVGs + app-server request JSON) under
`client-e2e/goldens/<scenario>/`. Generated by the existing e2e harness; no
Python CLI needed to run the gate.

- Generate: `make store_golden` from `vibe/`. For one scenario, use the pinned command from the `migrate-cli-to-rust` skill.
- Test: `make test_golden` from `vibe/`. The Makefile pins `pyte` and `rich`; unpinned versions can render different SVGs.
- Each scenario stores SVG snapshots and normalized client-to-server RPCs. `test_golden.py` also checks declared action, screen, and clipboard expectations.
- Regenerate when the Rust CLI intentionally changes rendering; review the committed diff.

## Running tests

Do not waste resources: when changes are focused, only run related test suites.

- If you only need a subset, don't run the full suite.
- Unit tests must never reach the host clipboard: the clipboard is a fail-closed port (`src/clipboard.rs`) — `main`/`bin/replay` install `SystemClipboard` at process start, the `ctor` in `tests/units.rs` installs `NullClipboard`, and `copy_to_clipboard` panics when no sink is installed. A standalone test binary that can reach a copy path must install a sink; client-e2e keeps setting `SSH_TTY` for the real binary.
- Changes under `src/ui/`, `src/selection/`, `src/mouse*`, or to `View` in `src/app.rs` affect rendering or copy, so they are related to the goldens: run `make test_golden`. This includes merge-conflict resolutions in those paths.
- No pre-commit hook runs the Rust tests: run `make test` from `vibe/` before pushing Rust changes.
- `make test_rust` runs the suite with cargo-nextest (per-test process isolation; a hung test fails fast via the `slow-timeout` in `cli-rust/.config/nextest.toml`). Install the runner locally with `cargo install cargo-nextest --locked --version 0.9.146`, the version CI installs.
- When running tests as an automated check (an agent verifying a change, a pre-push gate), pass `QUIET=1` (`make test_rust QUIET=1`, `make test QUIET=1`): nextest prints only failures and the summary, and the golden pytest run gets `-q`. Keep the full output for interactive debugging.
- When running terminal-lifecycle and golden tests in parallel, pick a worker count that fits the machine rather than a fixed `-n 10`: on CI run unconstrained (`-n auto`), locally use `-n max(cpu_threads/2 - 1, 1)`.
- If you're on the Rust side and haven't touched Python, skip the Python tests; if you do run them, target the relevant tests and never run them sequentially.

## other guidelines

- Colors are defined only in `src/ui/theme/` (fixed brand colors in `ui/theme/fixed.rs`); never write a color literal elsewhere
- Follow the `vibe-rust-tui` skill for shortcut hints, keyboard navigation (edges, back, digits), list scrolling, searchable lists (search model and search row position), selection highlights and colors
